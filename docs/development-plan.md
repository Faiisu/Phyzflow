# แผนพัฒนา Python-first AI Workspace

## เป้าหมาย

สร้าง Workspace สำหรับเขียน รัน ดีบัก และ deploy AI inference flow ด้วย Python นักพัฒนาใช้ IDE และ Git ตามปกติ ส่วน Web UI แสดงกราฟจากโค้ด ให้ทดลองรัน และช่วยไล่ผลลัพธ์หรือข้อผิดพลาดกลับไปถึง node และไฟล์ที่เกี่ยวข้อง

เวอร์ชันแรกรองรับหนึ่งโปรเจกต์ หนึ่ง Python environment ต่อการติดตั้ง และหนึ่ง flow แบบรับ request แล้วคืนผล ทดสอบตั้งแต่ติดตั้ง SDK ไปจนถึงให้ build ที่ deploy แล้วรับ request บนปลายทางหนึ่งแบบ

## ข้อกำหนดที่ใช้ตลอดการพัฒนา

- ติดตั้ง Workspace SDK ผ่าน `pyproject.toml` และใช้ CLI จาก Python environment ของโปรเจกต์เพื่อเปิด UI ในเบราว์เซอร์
- `flow.py` ประกาศ input, node, การเชื่อม dependency และ output แต่ละ node เป็นฟังก์ชัน Python ที่เรียกตรงและทดสอบแยกได้ มีไฟล์หลักที่อ้างกลับจากกราฟได้ เช่น `entrypoint.py` และแยกโค้ดเป็นไฟล์ย่อยหรือ subpackage ได้
- Runner เรียก node ใน Python process เดียวกันและส่งออบเจ็กต์ Python เช่น tensor หรือ DataFrame โดยตรง Runner ส่ง event และข้อมูลสรุปให้ CLI และ UI แยกจากข้อมูลที่ส่งระหว่าง node
- Node ใช้ dependencies ของโปรเจกต์ รวมถึง native code หรือ GPU ตามที่ environment รองรับ และเลือกเรียกโมเดลใน process หรือผ่าน endpoint จากโค้ด Python ได้
- CLI, การรันผ่าน UI และ deploy ใช้ตัวตรวจโปรเจกต์ชุดเดียวกัน

## ลำดับการพัฒนา

### 1. พิสูจน์เส้นทางจาก IDE ถึง Web UI

เลือก workload แรก ปลายทางที่คาดว่าจะใช้ และ Python version เบื้องต้นพร้อมเริ่มงาน SDK ใช้ข้อจำกัดของ workload เป็นข้อมูลเลือก environment แล้วทดสอบสมมติฐานในข้อ 2

1. **SDK และ CLI** สร้าง Python package และโปรเจกต์ตัวอย่างที่ประกาศ dependency ใน `pyproject.toml` ใช้ flow จัดประเภท ticket `Prepare → Predict → Decide` ให้ `Decide` รับทั้งข้อมูลจาก `Prepare` และผลจาก `Predict` ซึ่งเรียกไฟล์ย่อยและคืนผลคงที่ ใช้ sample input และ output ที่คาดไว้ชุดเดียวกันสำหรับ Python API, CLI และ UI
   - กำหนดวิธีอ้าง input ของ flow และ output ของ node ต้นทางเป็น argument ปลายทาง กราฟระบุ `step_id` ที่ไม่ซ้ำ ชื่อ node และตำแหน่งไฟล์ Runner เรียก node ตาม dependency และส่งออบเจ็กต์เดิมต่อ
   - ทำ `workspace check` และ `workspace run` ตรวจ syntax ของ `flow.py` และ Python source ในขอบเขต path ของโปรเจกต์ที่กำหนด รวมถึงไฟล์ย่อย ใช้ interpreter เป้าหมายก่อน import จากนั้นตรวจ import, entrypoint, dependency ที่อ้างถึง, cycle และ argument ที่เชื่อมผิดหรือขาด ให้การโหลด flow และโมดูลที่เกี่ยวข้องตรวจผ่านได้โดยยังไม่โหลดโมเดลหรือเรียกเครือข่าย
   - เมื่อ validation พัง ให้ระบุขั้นและไฟล์กับบรรทัดเมื่อมีข้อมูล เมื่อ node ล้มเหลว ให้ run เป็น `failed` และ node ปลายทางที่ต้องใช้ผลจาก node นั้นเป็น `skipped` ส่ง event ที่มี `run_id`, `step_id` สำหรับ event ระดับ node, สถานะ และเวลา พร้อมข้อมูล traceback สำหรับวินิจฉัย
2. **Web UI** เมื่อ CLI รัน flow ตัวอย่างได้ ให้เปิด localhost UI จาก CLI ทันที ใช้ตัวตรวจ กราฟ และ event ชุดเดียวกัน ให้เห็นเส้นเชื่อมและไฟล์ต้นทาง ใส่ sample input กด Run ดู output, สถานะสด และ traceback ให้ Runner เป็นเจ้าของ run ฝั่งเซิร์ฟเวอร์ และให้เริ่มคำสั่งเปิด UI ใหม่หลังแก้ source เพื่อโหลดโค้ดรุ่นที่แก้แล้วในเวอร์ชันแรก
3. **ตรวจ Runner และวัด baseline เบื้องต้น** หลังเส้นทาง CLI พร้อม ให้ทดสอบแยกด้วย CPU tensor ว่า node ปลายทางรับออบเจ็กต์เดิมและ device เดิม เปรียบเทียบการเรียกโค้ด flow โดยตรงกับ Runner ที่ไม่เปิด UI แล้วเพิ่มการวัด Runner พร้อม Live UI เมื่อพร้อม งานทดสอบและวัดทำคู่กับการต่อ UI ได้

**เกณฑ์จบ**

- ติดตั้งจาก repo ใน environment ใหม่ เรียก node โดยตรง และรันผ่าน Python API, CLI และ UI ด้วย sample เดียวกันแล้วได้ output ที่คาดไว้ กราฟแสดงทั้งเส้น `Prepare → Predict → Decide` และ `Prepare → Decide`
- ใช้ input ที่ทำให้ `Predict` โยน exception จากไฟล์ย่อย ทั้ง CLI และ UI แสดง `Predict` เป็น `failed` และ `Decide` เป็น `skipped` ผู้ทดลองที่ไม่เคยอ่าน flow ชี้ node, exception และไฟล์ต้นเหตุจาก UI ได้ แก้ไฟล์แล้วเปิด UI ใหม่ จากนั้นรันซ้ำและเห็นผลจากโค้ดที่แก้
- การทดสอบ `check` ครอบคลุม syntax ผิดในไฟล์ย่อย, import พัง, dependency ที่หาไม่เจอ, cycle และ argument ที่เชื่อมผิดหรือขาด โดยหยุดก่อนเรียกฟังก์ชันของ node และ flow ที่ถูกต้องตรวจผ่านโดยยังไม่โหลดโมเดล ผลทดสอบ tensor และคำสั่งวัด baseline ทำซ้ำได้

### 2. ทดลอง deploy กับ workload แรก

เริ่มเมื่อ CLI ในข้อ 1 รัน flow ตัวอย่างได้ งานนี้ทำคู่กับ Web UI ได้

- [ ] แพ็กโค้ดและ dependencies ของ workload แรก ติดตั้งใน environment สะอาดของปลายทางที่เลือก รัน `workspace check` แล้วทดสอบตัวรับ request ขั้นต่ำด้วยโมเดลจริงและ request/response ที่เป็นตัวแทน workload รวมถึง native dependency หรือ GPU หาก workload ต้องใช้
- [ ] บันทึกวิธี build, Python version, dependencies, การโหลดโมเดล และรูปแบบ request/response ที่ผ่านการทดลอง ใช้ตัวรับ request และตัวอย่างนี้ต่อในข้อ 3 หากทดลองไม่ผ่าน ให้แก้ SDK หรือปรับปลายทางแล้วทดสอบซ้ำก่อนทำ `workspace deploy`
- [ ] เมื่อ workload และ Live UI พร้อม ให้วัด baseline ของ workload จริงด้วยวิธีในข้อ 5 แล้วกำหนดเพดานส่วนเพิ่มของ latency p95 และ peak memory สำหรับ Runner ทั้งสองแบบเทียบกับการเรียกโค้ดโดยตรง ก่อนลงทุนกับประวัติการรัน งาน deploy เดินหน้าต่อได้เมื่อการทดลองปลายทางผ่าน

**เกณฑ์จบ** Build ใน environment เป้าหมายผ่าน `workspace check` รับ sample request ผ่านตัวรับ request และคืนผลที่คาดไว้ด้วยโมเดลและ dependencies ของ workload แรก ทำ build และทดสอบซ้ำได้จากคำสั่งที่บันทึกไว้

### 3. ส่งมอบ Deploy หนึ่งปลายทาง

- [ ] ทำ `workspace deploy` สำหรับปลายทางที่ผ่านข้อ 2 ให้ตรวจ build ใน Python environment เป้าหมาย ทดสอบผ่านตัวรับ request และเส้นทางแปลง request/response เดียวกับที่ให้บริการ จากนั้นเปิด traffic ให้ build ที่ผ่านการตรวจ สำหรับโปรเจกต์ทั่วไปให้รัน smoke test เมื่อมี sample input และผลที่คาดไว้ ส่วน workload แรกต้องมี smoke test ใน repo
- [ ] ให้ build ที่ deploy แล้วรายงานความผิดพลาดโดยอ้างถึง build, run, node และไฟล์ต้นทาง ใช้ข้อมูลวินิจฉัยที่ไม่บันทึก raw request หรือข้อความ exception ที่อาจมีค่าจาก request เป็นค่าเริ่มต้น

**เกณฑ์จบ** สั่ง deploy workload ที่ผ่านข้อ 2 จาก repo แล้วส่ง request จริงได้ ผลตอบกลับตรงที่คาดไว้ เมื่อส่ง request ที่จงใจทำให้ node ล้มเหลว สามารถระบุ build, run, node และไฟล์ได้ Build ที่มี syntax ผิด, import พัง หรือ smoke test ไม่ผ่านหยุดก่อนเปิด traffic พร้อมรายงานสาเหตุที่แก้ได้

### 4. เพิ่มประวัติการรันและข้อมูลดีบักใน Web UI

เริ่มได้เมื่อ UI ขั้นแรกและ baseline ของ workload พร้อม ใช้ประวัติสำหรับ run ใน Workspace ที่เปิดจาก CLI ส่วน run ที่ deploy แล้วใช้ข้อมูลวินิจฉัยจากข้อ 3

- [ ] บันทึกรหัสเวอร์ชันของ source ที่โหลดจริงและตำแหน่งไฟล์จากเวลาที่รัน ให้แยกการแก้ไฟล์ใน working tree ออกจาก commit เดิมได้ เช่น ใช้ fingerprint ของ source ที่โหลด
- [ ] เก็บสถานะ เวลา และ metadata เช่น `shape`, `dtype` และ `device` เป็นค่าเริ่มต้น สำหรับข้อผิดพลาด เก็บประเภท exception และตำแหน่งใน stack โดยตัดข้อความที่อาจมีข้อมูลจาก request ให้โค้ดบันทึกเหตุผลการตัดสินใจได้ และให้โปรเจกต์เปิดเก็บตัวอย่าง input/output เป็นราย node
- [ ] เพิ่มหน้าประวัติสำหรับดูระยะเวลา สรุป input/output สถานะ เหตุผลการตัดสินใจ และข้อมูลข้อผิดพลาดที่บันทึกไว้ ให้ Runner ทำงานต่อเมื่อหน้าเว็บปิดหรือหลุด และเปิดดูผลได้หลังเชื่อมต่อกลับมา

**เกณฑ์จบ** ผู้ทดลองปิดหน้าเว็บระหว่าง run แล้วกลับมาดูผลได้ เมื่อแก้ source และเริ่ม UI ใหม่ ประวัติยังแยก run เดิมจาก run ที่ใช้ source ใหม่ได้ รวมถึงกรณีแก้ไฟล์โดยยังไม่ commit ทดสอบด้วย request และ exception ที่มีค่าตัวอย่างเดียวกันแล้วตรวจว่าค่าดังกล่าวไม่ถูกเก็บโดยปริยาย

### 5. ทดสอบก่อนส่งมอบ

- [ ] วัด workload เป้าหมายอีกครั้งทั้งการเรียกโค้ดโดยตรง, Runner ที่ไม่เปิด UI และ Runner พร้อม Live UI ใช้ input, เครื่อง และ environment เดียวกัน วัด latency p50/p95 และ peak memory หลัง warm-up ระบุขอบเขต process และหน่วยความจำที่นับ ใช้วิธีเดียวกับ baseline ในข้อ 2
- [ ] ให้ผู้ใช้ใหม่ติดตั้งจาก repo เพิ่ม node ที่มีไฟล์ย่อย รัน flow และหาสาเหตุของ exception จาก UI สำหรับเคสที่รันสำเร็จแต่ให้ผลคลาดจากคาด ให้ใช้ตัวอย่างที่เปิดบันทึกเหตุผลการตัดสินใจหรือตัวอย่าง input/output ของ node ที่เกี่ยวข้อง แล้วให้ผู้ใช้ชี้ node และหลักฐานจาก UI สุดท้ายให้ deploy workload จากข้อ 3 และยืนยันว่าเรียกได้ เก็บจุดติดขัด แก้ และลองซ้ำ

**เกณฑ์จบ** ผู้ใช้ใหม่ทำเส้นทางข้างต้นได้จาก repo และคำสั่งที่บันทึกไว้ และผลวัดทำซ้ำได้โดยอยู่ในเพดานส่วนเพิ่มของ latency p95 และ peak memory ที่ตั้งไว้สำหรับ workload แรก
